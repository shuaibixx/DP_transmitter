## 1. 上板自检工具（先学会用它）

`main.c` 的 `app_scan_bus()` 在启动时对**两根 I²C 总线各做一次全地址扫描**。
这不是普通的地址查找，它同时给出三个关键判据：

```
sensor  PF0/PF1 idle SCL=1 SDA=1  drive SCL=1 SDA=1
    ack: 0x6D(expected)
display PA6/PA7 idle SCL=1 SDA=1  drive SCL=1 SDA=1
    ack: (none)
```

| 字段 | 怎么来的 | 含义 |
|---|---|---|
| **`idle SCL/SDA`** | 释放两条线后读回 | `1` = 线被拉高（有上拉）。`0` = **线被拉住**（缺上拉/短路/脚错了） |
| **`drive SCL/SDA`** | **主动拉低**再读回 | `1` = 引脚**能**拉低（GPIO 正常）。`0` = **引脚驱动不了**（配置错/脚被占） |
| **`ack: 0x..`** | 逐个地址发地址字节看应答 | 列出**所有应答的 7bit 地址**，覆盖 `0x08~0x77` |

### 为什么 `idle=1` 不能证明器件存在

代码里引脚开了内部上拉（`GPIO_PULL_UP`，约 40 kΩ），**即使总线上什么都没接，读回来也是 1**。
所以必须配合 `drive` 字段：`drive=1` 才说明引脚驱动正常，此时 `ack` 为空才能断定「总线上真没东西」。

### 读失败时会自动重扫

每 **16 次**读取失败（约 5 秒，300 ms/次）重扫一次总线，方便**边给器件上电/动线边观察**，
不用反复复位。

## 2. 调试时间线

### 阶段 0：读完资料，写完驱动（10-15 ~ 10-16）

- 从加密 PDF / TRAE 提取文本里拿到 HBP5023D-1 和 -2 的手册
- 写了完整的 6 个模块 + main，编译 0 错 0 警

### 阶段 1：第一次上板 —— 传感器完全不应答

```
sensor  PF0/PF1 idle SCL=1 SDA=1
    ack: (none)
display PA6/PA7 idle SCL=1 SDA=1
    ack: (none)
NO I2C ACK at 0x78
```

**当时的判断过程**：
1. 串口 banner 正常 → MCU 和 UART 没问题
2. 失败间隔 310 ms（正好是 `APP_SAMPLE_PERIOD_MS` + 一点）→ 说明是在**地址字节**就 NACK 了，不是转换超时
3. 但 `idle=1` 有歧义（内部上拉也能读 1）→ **于是加了 `drive` 测试**

### 阶段 2：加 drive 测试 —— 确认引脚没问题

```
sensor  PF0/PF1 idle SCL=1 SDA=1  drive SCL=1 SDA=1
    ack: (none)
```

`drive=1` → 引脚能拉低 → **固件侧排除**。同时对照了库的 `GPIO_InitPeripheral` 源码，
确认 OD 位 / PMODE / PUPD 都设对了。

### 阶段 3：换传感器型号（-1 → -2）

用户把传感器从 **HBP5023D-1**（0x78，`0xAC` 命令式）换成了 **HBP5023D-2**（0x6D，寄存器式）。
**驱动整个重写**。

### 阶段 4：传感器认到了！

```
sensor  PF0/PF1 idle SCL=1 SDA=1  drive SCL=1 SDA=1
    ack: 0x6D(expected)
```

**地址 0x6D 确认**（手册表3 对，附录的 0x6B 是错的）。

### 阶段 5：早期误判SCO（历史，已修正）

```
CONVERSION TIMEOUT (SCO never cleared), 0x30 reads 0x02
```

`0x30` 恒为 `0x02`（bit1 = SCO = 转换中），200 ms 不清零。

**分析**：启动命令写的是 `0x0A`（`00001010`），**本身就带 bit1**，
所以"SCO=1"符合"转换中"的预期 —— 问题只是它**永远不清**。

**采取的兜底**：手册第 3 步原文允许 *"或等待延迟 10 ms"*。
实现改成：轮询 SCO **50 ms** → 不清就**固定等 10 ms 硬读** → 标记 `(stuck!)`，
并把 `0x06~0x0A` 五个**原始字节**打印出来。

**⏳ 这一步的结果还没拿到**（用户此后转去做文档整理）。

## 3. 已确认的事实（不用再查）

| 事实 | 怎么确认的 |
|---|---|
| 传感器地址 **0x6D** | 总线扫描实测 `ack: 0x6D` |
| 手册附录的 0x6B/0xD6 是错的 | 同上；表3 的位模式 `1101101` = 0x6D |
| PF0/PF1 引脚驱动正常 | `drive SCL=1 SDA=1` |
| 两条总线都能正常工作 | 同上，两根线都通过 |
| 固件 GPIO 配置正确 | `drive` 测试 + 对照库源码 |
| **PA2/PA3 = USART2 + AF4** | 官方 USART 例程；编译时函数重名才发现 |
| N32G031 **没有 TIM14** | 头文件里只有 TIM1/2/3/6/8/18 |
| N32G031 **只有 GPIOA/B/C/F** | 手册 2.25 节 + 头文件 |

## 4. 踩过的坑（都有代价，别再踩）

| # | 坑 | 现象 | 解决 |
|---|---|---|---|
| 1 | 自定义 `USART_Init()` 和库重名 | `error: #147-D declaration is incompatible` + `too many arguments` | 改名 `USART_Debug_Init()` |
| 2 | 以为 PA2/PA3 是 USART1 | 编译报错才发现 | 官方例程是 **USART2 + `GPIO_AF4_USART2`**，时钟在 **APB1** |
| 3 | 引用了 GPIOD/GPIOE | 编译报未定义 | N32G031 只有 **A/B/C/F** 四组 |
| 4 | 把 -2 当成 -1 的协议 | 完全读不到 | 两个型号**协议不兼容**，重写驱动 |
| 5 | 信了手册附录的 0x6B | 扫不到 | **表3 才权威：0x6D** |
| 6 | TIM 比较寄存器写成 CCR1 | 编译报未定义 | 是 **`CCDAT1`** |
| 7 | 商家 OLED 字库越界 | 显示 `{~|}` 等字符可能读飞 | 加 `sizeof` 边界保护 |
| 8 | 失败提示每 310 ms 刷一次屏 | 串口被淹没 | 详细原因只打一次，之后打短行 |
| 9 | `else` 分支里重复调用了一次 `HBP5023_Read()` | 浪费一倍时间、而且传参是布尔值 | 改成先存 `result` 再判断 |
| 10 | `app_pressure_to_current` 在测试模式下未使用 | `warning #177-D declared but never referenced` | 用 `#if !APP_SENSOR_TEST_ONLY` 包起来 |
